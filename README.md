# Практична робота №15

## Безпека клієнтських застосунків: типові вразливості та захист

### Формат

Комп'ютерний практикум

### Мета роботи

Провести аудит застосунку «Список бажань» (весь проєкт практикумів 1–14) на три типові клієнтські проблеми: XSS через `innerHTML`, зайві чи чутливі дані в localStorage/IndexedDB і роль HTTPS. Потрібно усунути щонайменше одну реальну вразливість і показати різницю «до» і «після».

### Варіант завдання

**Варіант 7 — Список бажань (Wishlist)**

| Що перевіряється | Поле | Ризик |
|---|---|---|
| XSS | `title` — назва бажання, яку вводить користувач | HTML у назві виконається, якщо її вставити через `innerHTML` |
| Сховище | `url` — посилання на товар | посилання з `javascript:` потрапить у `href` і виконає скрипт |

### Хід роботи

**Крок 1. Пошук усіх місць `innerHTML`**
Пошуком у VS Code (`Ctrl+Shift+F`) перевірено `innerHTML`, `v-html`, `outerHTML`, `insertAdjacentHTML` і `document.write`. Результат такий:
- єдиний `innerHTML` (`listContainer.innerHTML = ''`) лишився в закоментованій функції `renderWishes` з практикуму 7 і не виконується;
- `v-html` не використовується ніде.

Назва бажання (`title`) виводиться через інтерполяцію Vue `{{ title }}`, яка завжди екранує текст. Тому `title` вже захищене від XSS.

**Крок 2. Підтвердження вразливості**
- **`title`.** У поле «Назва бажання» введено тестовий рядок `<img src=x onerror="alert('XSS')">`. Alert не з'явився: рядок відображається на картці як звичайний текст. Інтерполяція `{{ }}` працює як `textContent`.
- **`url`.** У поле «Посилання на товар» введено `javascript:alert('XSS')`. Поле `type="url"` його пропускає, бо формально це коректна URL-адреса. Значення зберігається в IndexedDB і без перевірки підставляється в `:href` посилань «Переглянути товар» і на сторінці деталей.

  У DevTools → Elements видно `href="javascript:alert('XSS')"`. Якщо в консолі прибрати `target="_blank"` і клікнути посилання, з'являється alert:
  ```js
  document.querySelector('.wish__link').removeAttribute('target');
  ```
  Тобто код зі сховища виконується в контексті сторінки. Від цього зараз випадково рятує лише `target="_blank"`.

**Крок 3. Виправлення**
У `script.js` додано функцію `safeUrl`. Вона пропускає лише абсолютні посилання зі схемою `http:` або `https:`, а все інше (`javascript:`, `data:`, `vbscript:`, відносні шляхи, некоректні рядки) повертає як порожній рядок:

```js
function safeUrl(value) {
  if (!value) {
    return "";
  }
  try {
    const parsed = new URL(value);
    return parsed.protocol === "http:" || parsed.protocol === "https:" ? parsed.href : "";
  } catch {
    return "";
  }
}
```

Перевірка стоїть у кількох місцях, бо небезпечне значення може прийти з різних джерел:
1. **`addWish`** — форма не додає бажання з небезпечним посиланням і показує повідомлення «Посилання має починатися з http:// або https://». У полі також є атрибут `pattern="https?://.+"`.
2. **`importFromApi`** — дані з сервера теж проходять через `safeUrl`. Довіра до джерела не скасовує перевірку.
3. **`WishItem`** — обчислювана властивість `safeHref`. Посилання «Переглянути товар» показується лише для безпечної адреси. Це захищає й від записів, які вже лежать в IndexedDB.
4. **Сторінка деталей** — обчислювана властивість `currentWishHref`.

**Крок 4. Перевірка після виправлення**
- Повторне введення `javascript:alert('XSS')` у форму показує повідомлення про помилку, і бажання не додається.
- Для старого запису з таким посиланням в IndexedDB кнопка «Переглянути товар» більше не з'являється.
- На сторінці деталей адреса виводиться лише як текст.
- Рядок `<img src=x onerror="alert('XSS')">` у назві, як і раніше, відображається текстом.

**Крок 5. Огляд інших місць**

| Місце | Дані | Висновок |
|---|---|---|
| `{{ title }}`, `{{ currentWish.title }}` | введення користувача | безпечно, Vue екранує |
| `:alt="title"` | введення користувача | безпечно, значення атрибута екранується |
| `:href="url"`, `:href="currentWish.url"` | введення користувача, сервер | **виправлено** через `safeUrl` |
| `:src="image"` | сервер | безпечно, `javascript:` у `src` браузери не виконують |
| `{{ statusText }}`, `{{ storageError }}` | власні тексти застосунку | безпечно |
| `innerHTML` у `renderWishes` | — | закоментований код практикуму 7, не виконується |

**Крок 6. Дані в localStorage / IndexedDB**
У DevTools → Application переглянуто:
- **localStorage:** лише `wishlistMigrated = true` (прапорець одноразової міграції). Ключ `wishlistItems` з'являється тільки в спрощеному режимі, коли IndexedDB недоступна, тому в основному режимі його немає.
- **IndexedDB:** `WishlistDB` → `wishes` із полями `id`, `title`, `price`, `url`, `priority`, `image`, `purchased`, `saved`.

**Висновок:** у сховищі є лише назви, ціни й посилання на товари. Паролів, токенів, email, телефону чи платіжних даних там немає. Ці дані не є чутливими, але сховище доступне будь-якому скрипту на сторінці. Тому значення звідти (як-от `url`) перевіряються перед використанням.

**Крок 7. Захардкоджені секрети**
Код перевірено на `key`, `token`, `password` і `secret` — нічого не знайдено. Застосунок звертається лише до власного локального API `/api/wishes` (практикум 14), якому ключі не потрібні. Email і телефон у футері — публічні контакти автора, а не секрети.

**Крок 8. HTTPS при розгортанні**
Під час розробки використовується `http://localhost:3000`. Localhost браузери вважають безпечним контекстом, тому HTTPS тут не потрібен.

Для фінальної здачі обрано **GitHub Pages**, де HTTPS увімкнено за замовчуванням (`https://mrnemxjeka.github.io/lab15/`). GitHub Pages роздає лише статику, тому без Node-сервера кнопка «Завантажити з сервера» покаже повідомлення про помилку, а сам список працює з IndexedDB. Для розгортання разом із сервером підійде Render або Vercel, де HTTPS теж увімкнено за замовчуванням.

### Висновок

У ході практичної роботи №15 проведено аудит безпеки застосунку «Список бажань». Пошук `innerHTML` і `v-html` показав, що назва бажання (`title`) захищена від XSS: Vue виводить її через інтерполяцію `{{ }}`, яка екранує HTML, тому тестовий рядок `<img src=x onerror="alert('XSS')">` відображається як звичайний текст.

Реальна вразливість знайдена в полі `url`: посилання зі схемою `javascript:` зберігалося в IndexedDB і без перевірки потрапляло в `href`. Її усунуто функцією `safeUrl`, яка пропускає лише адреси `http:` і `https:`. Перевірка стоїть у формі, під час завантаження даних із сервера і під час виведення посилань, тому працює і для вже збережених записів.

У localStorage та IndexedDB немає чутливих даних (паролів, токенів, особистої інформації), а в коді немає захардкоджених секретів. Для розробки достатньо localhost, а для фінальної здачі обрано GitHub Pages з HTTPS за замовчуванням.

Отже, дані користувача, сервера чи сховища не можна вставляти в розмітку або атрибути без екранування й перевірки.
